# Building Course2Career’s AI Sales Force: A Production Blueprint Using LangGraph, GenX, and Real-Time Voice Pipelines

This report provides a comprehensive research analysis and architectural blueprint for developing a ChatGPT-like AI sales assistant for Course2Career. The system is designed to be powered exclusively by GenX's 60 models and must support real-time call coaching, post-call automation within Genie CRM and Outlook, and a multi-agent architecture. The primary objective is to deliver a functional prototype by Monday, August 17, 2026, while ensuring the system is extensible and built upon robust, open-source technologies.

## AI Agent Orchestration Framework Selection

The selection of an AI agent orchestration framework is the foundational decision that will dictate the system's complexity, scalability, reliability, and development velocity. For this project, which requires executing complex, rule-based workflows with high reliability, the choice between leading frameworks—LangGraph, CrewAI, and AutoGen—is critical. While all three are powerful open-source tools, they embody different philosophies and are suited for distinct use cases [[143]]. In 2026, the landscape has matured significantly, moving beyond simple agent creation towards production-grade, stateful systems [[1]].

CrewAI is frequently highlighted as the fastest path to a working multi-agent prototype [[4,184]]. Its core abstraction is the "crew," a team of role-playing agents defined by a clear role, goal, and backstory [[1,66]]. This approach maps intuitively to business workflows and allows for rapid assembly of specialized agents [[4]]. Since version 1.0, CrewAI has incorporated Flows, which add event-driven workflows with conditional branching, enhancing its ability to handle deterministic business logic around agent autonomy [[2]]. However, CrewAI is considered a higher-level framework, prioritizing developer speed and ease of use over the fine-grained control offered by lower-level alternatives [[3,197]]. While excellent for quickly validating concepts and building teams of role-based agents, its less explicit control flow may not be sufficient for the highly structured and error-sensitive processes required for CRM management [[4]].

AutoGen, developed by Microsoft Research, was a pioneering framework that popularized the concept of multi-agent conversational systems where agents collaborate by talking to each other [[31,32]]. It is particularly well-suited for scenarios involving human-in-the-loop collaboration and distributed deployments due to its event-driven, actor-style architecture [[1,4]]. However, the ecosystem has evolved. As of April 2026, Microsoft merged AutoGen and Semantic Kernel into a unified **Microsoft Agent Framework**, making many older resources and tutorials about standalone AutoGen outdated [[65,140]]. While still a powerful tool, especially for Azure-native enterprises, its focus on conversational dynamics might be less aligned with the project's need for deterministic, state-managed workflow execution compared to more graph-oriented frameworks [[1]]. Furthermore, its flexibility can come at the cost of scalability and a steeper learning curve for complex systems [[122]].

LangGraph emerges as the most suitable choice for this project, primarily because it is widely regarded as the de facto standard for production-grade, stateful multi-agent systems [[1,203]]. Unlike CrewAI's role-based abstractions or AutoGen's conversational loops, LangGraph treats agent applications as stateful graphs [[142,177]]. Each node in the graph represents a step in the workflow (e.g., a function or an agent), and edges represent transitions between steps, which can be conditional [[3]]. This graph-based mental model provides developers with explicit, deterministic control over every aspect of the workflow, including loops, branching, error handling, and human-in-the-loop interruptions [[1,178]]. This level of granular control is paramount for reliably executing the intricate, sequential logic required for automating lead management in Genie CRM, as specified in the user's detailed task definitions [[170]]. The framework's ability to implement patterns like the "Supervisor" is a perfect fit for the user's request for a multi-agent system; a supervisor agent can receive a high-level task, delegate sub-tasks to specialized agents (like a `GenieCRMAgent` or a `CommunicationAgent`), and manage their collaboration [[3]].

Furthermore, LangGraph's deep integration with the broader LangChain ecosystem is a significant advantage [[3]]. This provides access to thousands of pre-built integrations for various data sources, APIs, and LLM providers, dramatically accelerating development. Crucially, it integrates seamlessly with LangSmith, a dedicated observability platform for debugging, testing, and monitoring complex agentic workflows [[1,3]]. For a system as mission-critical as a sales assistant, the ability to trace a request through multiple agent interactions, inspect intermediate states, and debug failures is not just beneficial—it is essential for long-term maintainability and reliability. Other frameworks offer less mature or integrated observability solutions [[4]]. While CrewAI and LangGraph are both battle-tested and suitable for production, LangGraph's explicit control makes it superior for workflows requiring guaranteed execution order and robust error handling [[178,203]]. ## Real-Time Voice Interaction Pipeline Architecture

The requirement for real-time call coaching during sales calls presents the most significant technical challenge of the project. Achieving a natural, low-latency interaction where the AI assistant can listen, process, and provide audible feedback without disrupting the conversation demands a carefully architected streaming pipeline. The industry-standard approach for enterprise-grade real-time voice agents is a cascaded streaming pipeline, composed of three main stages: Speech-to-Text (STT), Large Language Model (LLM), and Text-to-Speech (TTS) [[39,40]]. This architecture allows for modularity, flexibility in model selection, and component-specific optimization, which is crucial for meeting strict latency budgets [[39]].

The foundation of this architecture is efficient media transport. For browser or mobile clients, WebRTC is the optimal protocol due to its low setup latency (100-400ms), efficient wideband Opus audio codec (which improves STT accuracy), and direct control over the media path [[35]]. To manage media streams efficiently, especially in a multi-user environment, a Selective Forwarding Unit (SFU) server is recommended. Open-source SFUs like those used with the LiveKit framework can handle the distribution of audio streams to backend workers with minimal overhead, simplifying the agent worker's plumbing [[36,39]]. The agent worker itself receives clean RTP packets from the SFU, decodes them into audio, and passes them to the STT service for transcription [[36]].

The first stage, **Speech-to-Text (STT)**, is responsible for converting the spoken words of the sales representative and the prospect into text. For real-time performance, the STT service must support streaming, meaning it begins transcribing as soon as it receives audio, rather than waiting for the entire utterance to complete. This streaming capability is non-negotiable; batch processing would introduce delays of 600-1200ms before the LLM could even be called, making sub-second interaction impossible [[35]]. Deepgram's Nova-3 model is frequently cited as a top-tier commercial option for streaming STT, offering a first-word latency of 60-80ms over WebSocket [[35]]. Key configurations include setting `endpointing=300` to allow the service to detect silence and end-of-turn automatically, which helps manage turn-taking [[35]]. While open-source models like Whisper exist, commercial APIs often provide better performance on noisy or accented speech, which is common in real-world sales calls [[35]]. A critical step before any transcript reaches the LLM is pre-LLM PII redaction. Sensitive information should be stripped from the raw audio or transcript within the agent worker using regex patterns or a Named Entity Recognition (NER) model to comply with data privacy regulations [[35]].

The second stage is the **Large Language Model (LLM)**, which serves as the brain of the operation. The GenX Router provides a single, unified REST endpoint (`https://query.genx.sh/api/v1`) to access over 40 AI models from various providers, abstracting away the complexity of managing multiple API keys [[135]]. For real-time coaching, the most critical metric is the Time-To-First-Token (TTFT). Conversational linguistics research suggests that a median response gap of 200ms is the threshold for natural conversation; gaps beyond 500ms cause users to interrupt or disengage [[35]]. Therefore, selecting a low-latency LLM is paramount. Models hosted on specialized hardware platforms like Groq (e.g., Llama 3.3 70B with TTFT under 80ms) or commercially available models like Claude Haiku 4.5 (~100-150ms TTFT) are prime candidates [[35]]. The GenX Router supports token streaming via Server-Sent Events (SSE), which is compatible with OpenAI and Anthropic SDKs, making it straightforward to integrate into the pipeline [[135]]. The LLM's prompt engineering is also critical; it must be designed to take the ongoing conversation transcript, the current context, and potentially a list of relevant "battle cards" or objection-handling scripts, and generate a concise, actionable tip for the sales rep [[10]].

The final stage is **Text-to-Speech (TTS)**, which converts the LLM's textual response back into audible speech. Similar to STT, the TTS service must stream audio chunks to avoid introducing significant delay. Cartesia Sonic is recognized as the fastest production TTS available, delivering the first audio chunk in 40-60ms [[35]]. ElevenLabs Flash (`eleven_flash_v2_5`) is another strong alternative, offering higher voice quality with a similar latency profile [[35]]. To achieve a natural flow, the LLM's response generation and the TTS audio synthesis can overlap. By streaming the LLM's output as soon as tokens are generated, the system can begin synthesizing the audio for the beginning of the response while the LLM is still generating the rest of the sentence, recovering 100-200ms of latency [[35]].

To orchestrate this entire pipeline, open-source frameworks are indispensable. **Pipecat** is a Python framework specifically designed for building real-time voice and multimodal conversational agents [[37]]. It is described as "voice-first," supporting pluggable integrations with numerous STT, LLM, and TTS providers, and enabling developers to easily swap out components without rewriting the pipeline [[37,38]]. Its composable pipeline architecture and official SDKs for multiple languages make it an excellent choice for rapid development [[37]]. Another strong contender is **LiveKit Agents**, an open-source agent framework built on the LiveKit WebRTC infrastructure [[42]]. It provides a session-based architecture with first-class support for function calling, allowing the agent to interact with external tools like the Genie CRM API directly from the LLM's response [[40]]. Both frameworks provide the necessary abstractions to build, test, and deploy the complex real-time interaction logic required for live call coaching.

Achieving a total end-to-end latency budget of 230-560ms is challenging but feasible with the right stack [[35]]. This budget includes network transport (20-60ms), Voice Activity Detection (VAD) (10-30ms), STT (60-120ms), LLM TTFT (100-250ms), and TTS (40-100ms) [[35]]. The dominant tuning areas are end-of-turn detection and LLM TTFT [[39]]. Managing turn-taking naturally, including handling interruptions (barge-ins), requires a sophisticated system that combines continuous VAD, an ML model to score when a speaker has finished talking, and instant TTS pre-emption to cancel an ongoing response when the user starts speaking [[39]]. This entire voice interaction pipeline can be managed by a LangGraph agent, which receives the streamed transcript, invokes the appropriate tools, and orchestrates the response through the TTS engine.

## Multi-Agent System Design and Integration Strategy

A successful implementation of the Course2Career AI assistant hinges on a well-defined multi-agent architecture and a flexible integration strategy. The user explicitly requested a system with specialized agents (e.g., prompt agent, CRM agent, communication agent), a design philosophy that aligns perfectly with modern agentic AI patterns [[5]]. This modular approach allows for specialization, easier maintenance, and the ability to scale by adding new agents for new functions. The core of this architecture will be built using LangGraph, which enables the creation of a "supervisor" agent that delegates tasks to these specialized sub-agents [[3]].

The proposed multi-agent system would consist of several key agents, each with a distinct role and a set of specialized tools:

1.  **The Supervisor Agent:** This central agent is responsible for receiving high-level commands from the user (e.g., "Process last week's calls") or from events (e.g., a webhook from a call recording service). It analyzes the task, determines which sub-agents are needed, and orchestrates their execution. It manages the state of the overall workflow, handles errors, and ensures that tasks are completed in the correct sequence [[3]].

2.  **The GenieCRM Agent:** This agent is the workhorse for all CRM-related tasks. Its sole responsibility is to interact with the Genie CRM API to execute the complex business logic provided by the user. Its tools would include functions to:
    *   Fetch lead details, existing tasks, and opportunity records.
    *   Create, update, or close tasks based on predefined rules (e.g., moving from "Pending First Call" to scheduling "Call 2").
    *   Update the status of opportunities according to the strict sequence rules (e.g., closing an opportunity to "Lost – No Show" if it's in the "Attempting Contact" stage after a final unsuccessful attempt).
    *   Ensure historical data is never altered and only active/open tasks or opportunities are modified [[170]].
    *   To meet the requirement of easy extensibility, this agent's tools should be built using a generic tool interface abstraction. This means the underlying code for interacting with Genie CRM would be encapsulated, and a new tool for a different CRM (like Salesforce or HubSpot) could be implemented by creating a new class that conforms to the same interface, without changing the core logic of the agent [[8]].

3.  **The Communication Agent:** This agent is responsible for all outbound communication tasks, primarily via Outlook. Its tools would leverage the Microsoft Graph API to perform actions such as:
    *   Sending personalized emails using saved templates and specific subject lines [[112]].
    *   Dispatching SMS messages from a designated number (+447428000560) using saved snippets [[170]].
    *   Creating calendar events for scheduled calls and follow-ups.
    *   Reading from specific mail folders to gather context [[71]].

4.  **The Real-Time Coach Agent:** This agent operates within the live call coaching pipeline. It receives the streaming transcription from the STT service. Its job is to analyze the conversation in real time, identify keywords or phrases indicating a need for assistance (e.g., a prospect raising an objection), and then retrieve and format a relevant coaching tip or battle card. This tip is then passed to the TTS engine to be spoken back to the sales representative. This agent's effectiveness relies heavily on prompt engineering and a well-curated knowledge base of coaching materials [[10]].

5.  **The Data Analysis Agent:** This agent would be triggered post-call to perform deeper analysis. It could summarize the call, extract key entities (stakeholders, competitors, products mentioned), and populate structured fields in the CRM, going beyond simple notes to create true "CRM intelligence" [[33]]. This agent would use GenX's models for summarization and entity extraction.

The integration strategy must be designed for both robustness and flexibility. The system will act as a client to both the Genie CRM API and the Microsoft Graph API. For authentication, a hybrid approach is recommended. For actions that are deeply personal to a user, such as reading their specific inbox or viewing their own calendar, **delegated permissions** are appropriate [[20,165]]. These permissions grant the application the same rights as the signed-in user, providing a secure and context-aware way to operate. The app registration in Azure AD would request specific scopes like `Mail.Read` [[23]].

However, for the core automation functions—the `GenieCRM Agent` updating records and the `Communication Agent` sending emails on behalf of the system without a specific user initiating the action—a more powerful authentication method is required. This is where **application permissions** and the OAuth 2.0 client credentials flow become essential [[128]]. This flow allows the application to authenticate as itself (its identity in Azure AD) and gain access to resources independently of any user's sign-in [[124]]. For example, the `Mail.Send` application permission grants the ability to send mail from the application's mailbox or, with proper configuration, on behalf of other users [[126]]. It is important to note that sending mail on behalf of other users typically requires specific licensing (e.g., Microsoft 365 Business license) and administrative policies to be configured [[148,186]]. This application permission model is far better suited for the background, service-oriented tasks that define the assistant's value proposition. The dashboard would allow administrators to configure which user's identity the service uses for these automated actions. Using Azure Managed Identity is a secure way to manage the application's credentials without hardcoding secrets in the source code [[173]].

By combining a modular, role-based agent design with a flexible authentication strategy that leverages both delegated and application permissions, the system can effectively and securely automate complex workflows across multiple platforms, fulfilling the user's vision for a powerful and extensible AI assistant.

## Post-Call Automation and CRM/Outlook Workflow Execution

The backbone of the Course2Career AI assistant is its ability to execute a series of precise, rule-based actions in Genie CRM and Outlook following a sales call. This post-call automation eliminates manual data entry and ensures consistent adherence to the company's established sales processes. The logic is complex and detailed, requiring careful implementation to avoid unintended consequences like altering historical data or creating duplicate tasks [[170]]. The system will rely on the `GenieCRM Agent` and the `Communication Agent`, orchestrated by LangGraph, to carry out these workflows reliably.

The automation process begins immediately after a call concludes. A trigger mechanism, likely a webhook sent from a telephony provider or a call recording service, initiates a workflow in the assistant's backend [[52,180]]. The Supervisor Agent receives this trigger and determines the appropriate workflow based on contextual clues, such as the duration of the call or metadata associated with the call. Two primary workflows, as defined in the user's detailed prompts, will be implemented.

**Workflow 1: Lead Follow-Up Sequence**
This workflow is designed to manage the progression of a sales lead through a predefined sequence of contact attempts. The process involves several critical checks to ensure data integrity and prevent the automation from interfering with completed activities.
*   **Step 1: Initial Assessment.** The `GenieCRM Agent` first fetches the candidate's full record from Genie CRM, including all existing tasks, conversation history, and opportunities [[170]]. It applies a filter to exclude any leads that have already been successfully contacted or are in a progressed state like "Pitched," "Not Interested," or "Closed" [[170]].
*   **Step 2: Task Management.** The agent then locates the currently active/pending task. Following the strict four-attempt sequence, it closes the current task (e.g., "Last Try Cyber") and schedules the next one ("Final Attempt Cyber") if applicable [[170]]. A crucial check is performed here: the agent verifies that no future callback task exists before proceeding, and it never reopens or alters any previously completed tasks [[170]]. This prevents the automation from accidentally reactivating a stale or resolved activity.
*   **Step 3: Opportunity Status Update.** The agent reviews all opportunities on the candidate's profile. A key rule is that an existing historical opportunity marked as "Lost" does not prevent the automation from acting on a current, open opportunity [[170]]. The agent identifies the most recent, active opportunity and updates its stage based on its current state:
    *   If the opportunity is "New Lead – Uncontacted" or "Attempting Contact," it is closed with the reason "Lost – No Show."
    *   If the opportunity is "Discovery Call Completed – Considering Options," it is closed with the reason "Not a Fit / Rejected."
    *   If there is no current/open opportunity, the agent skips the opportunity update step entirely [[170]].
*   **Step 4: Final Status and Communications.** Once all tasks and opportunities are updated, the agent sets the candidate's overall status to "Lost." It then dispatches the required communications. The `Communication Agent` sends the "Permission to Close Your File" email using a saved template and the associated subject line, ensuring no blank-subject emails are sent [[170]]. Simultaneously, it sends the "close file cyber" SMS from the designated number (+447428000560) [[170]].

**Workflow 2: Post-Consultation Follow-Up**
This workflow is triggered after a successful initial consultation and is designed to nurture the prospect. The outcome of the follow-up call determines the subsequent actions.
*   **Step 1: Task Completion.** The `GenieCRM Agent` locates and closes the "Yes/No Cyber" task, which corresponds to the follow-up call just completed [[170]].
*   **Step 2: Notes and Opportunity Update.** The agent adds a summary of the call outcome to the candidate's notes section. If the call was a success, it updates the opportunity stage to "Discovery Completed – Considering Options" if it isn't already there [[170]]. Critically, if the call was unsuccessful (no answer or voicemail), the agent triggers a different branch of the workflow.
*   **Step 3: Failed Contact Sequence.** Upon detecting an unsuccessful call, the Supervisor Agent directs the `Communication Agent` to execute a multi-channel outreach sequence. This includes sending the "Follow-up Email Cyber" from the saved templates, dispatching the "Failed Follow-up Cyber" SMS, and sending the "tried_to_email" WhatsApp message [[170]]. After this sequence is complete, the agent schedules the final "Last Try Cyber" task for the candidate [[170]].

For both workflows, the system must incorporate robust **duplicate protection**. Before performing any action, the agent must check whether that action has already been completed. This involves verifying if the target task already exists, if the email/SMS has already been sent, or if the opportunity has already been closed with the intended reason [[170]]. This idempotency is crucial for preventing data corruption in case the same webhook is received multiple times or if the workflow is manually re-triggered [[194]].

All API calls to Genie CRM and Microsoft Graph must be wrapped in comprehensive logging and error handling. The LangSmith observability platform, integrated with LangGraph, will be invaluable for tracking each step of these workflows, inspecting inputs and outputs, and diagnosing any failures in a production environment [[1]]. This ensures that the automation is not only powerful but also transparent and reliable, giving the sales team confidence that the system is correctly executing their business rules.

# 15. Local AI hardware reality

If you run your own AI, the software is free, but the hardware is not.

## CPU-only VPS

A normal Webdock VPS without GPU can run:

- Whisper base/small
- small embedding models
- maybe a tiny 1B–3B model slowly

It is not ideal for a full 7B/14B chat model if you want fast responses.

---

## GPU server

For proper local AI, you want GPU.

Examples:

### 8GB VRAM GPU

Can run:

- 7B models quantised
- Whisper medium
- embeddings

Okay for basic assistant.

### 12GB–16GB VRAM GPU

Can run:

- 7B models comfortably
- 14B models quantised
- faster Whisper
- better local writing model

Better for internal production.

### 24GB VRAM GPU

Can run:

- larger 14B/32B quantised models
- multiple local services
- better quality

Best for small team.

### 70B models

Not realistic for one normal VPS.

You need serious GPU setup.

```yaml
    image: caddy

      - "80:80"

      - ./caddy/Caddyfile:/etc/caddy/Caddyfile
      - caddy_data:/data

  db:
    image: pgvector/pgvector:pg16
    restart: always
    environment:
      POSTGRES_DB: c2c_assistant
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - ./db:/var/lib/postgresql/data

  redis:
    image: redis
    restart: always

  openwebui:
    image: ghcr.io/open-webui/open-webui:main
    restart: always
    environment:
      - OPENAI_API_BASE_URL=${GENX_BASE_URL}
      - OPENAI_API_KEY=${GENX_API_KEY}
    volumes:
      - ./web/data:/app/backend/data

  api:
    build: ./api
    restart: always
    env_file:
      - .env
    depends_on:
      - db
      - redis

  worker:
    build: ./worker
    restart: always
    env_file:
      - .env
    depends_on:
      - db
      - redis
      - browser

  browser:
    image: browserless/chrome
    restart: always

  whisper:
    build: ./whisper
    restart: always
    volumes:
      - ./files:/files
```

This is the shape. Exact config will depend on your domains and chosen images.
